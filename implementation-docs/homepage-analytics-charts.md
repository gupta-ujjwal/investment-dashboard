# Plan: Homepage analytics — design and implement the right charts (issue #9)

> Generated by `/brainstorm-lite` on 2026-05-16. Working notes at `notes/homepage-analytics-charts/`.

## Frame
- **Kind**: feature
- **Files/modules likely touched**: `src/storage/holdings.ts` (DB_VERSION 2→3 migration), new `src/storage/history.ts`, `src/routes/import/PreviewStep.tsx` (snapshot write after commit), `src/App.tsx` (`dashboardLoader` loads history), `src/routes/AnalyticsRoute.tsx` (KPI rework + charts), new `src/lib/analytics.ts` (pure aggregation), new `src/components/charts/*` (four Recharts components), `src/featureFlags.ts` (`FEATURE_HISTORY`), `package.json` (Recharts).
- **External surface affected**: IndexedDB schema — `DB_VERSION` 2→3, new additive `historySnapshots` object store via the existing staged `upgrade` callback. New npm dependency (Recharts). No public API/CLI.
- **Out of scope**: per-holding history drill-down UI (data captured, no screen), live/intraday price feed, day-change numbers, the dedicated deeper analytics tab.

## Research summary
- The homepage **is** `/analytics` — `App.tsx:88` redirects there when holdings exist; `AnalyticsRoute` currently shows four cost-basis KPI tiles + three "Coming online" `ChartFrame` placeholders (`AnalyticsRoute.tsx:38-72`).
- `CanonicalHolding` (`storage/holdings.ts:9-31`) stores **one** `currentPrice` per holding, overwritten each import — no time dimension, so time-series charts need new storage. No charting library is installed.
- `deriveRows()` (`holdingsView.ts:48-87`) already computes `investedBase`, `currentValueBase`, `profitAbsBase`, `profitPct`, `isStale` — chart aggregation reuses it, no re-derivation.
- `commitImport` has **two** callers: the import wizard (`PreviewStep.tsx:50`) and FX re-stamping (`refreshFx.ts:51,69`). The snapshot must fire only on the former — writing it from `PreviewStep` excludes the FX path for free.
- `getDB()` `upgrade` (`storage/holdings.ts:42`) already does staged migrations (`oldVersion < 1`, `< 2`); add an `oldVersion < 3` branch in the same shape.
- `Settings.baseCurrency` (`settings.ts:5-13`) is user-changeable — a snapshot must store the base currency it was computed in, or re-basing later mislabels old history.
- `lib/format.ts` has `formatMoney`/`formatPercent`/`formatDate` (all non-finite-safe) for axes and tooltips.

## Approaches considered

### Approach 1: Snapshot written from PreviewStep (recommended)
`recordSnapshot()` lives in new `storage/history.ts`, called from `PreviewStep.handleCommit()` immediately after `commitImport` resolves; it does its own `getAll()` to capture post-commit state. Touches `storage/holdings.ts` (migration only), new `storage/history.ts`, `PreviewStep.tsx`. Primitive: *add* a new cold-path code path, leaving `commitImport` pure. Risk: a snapshot write that fails after a successful commit leaves a history gap — mitigated by try/catch + `console.warn`, never blocking the "Import complete" screen (history is best-effort; holdings are truth). Complexity: small–medium, driven by the four Recharts components + restyle. Cleanly excludes the FX-refresh caller of `commitImport` with zero special-casing.

### Approach 2: Snapshot written inside `commitImport` behind a flag
`commitImport` gains a `recordHistory?: boolean`; `PreviewStep` passes `true`, `refreshFx` omits it. Touches `storage/holdings.ts` (migration + `commitImport`), `PreviewStep.tsx`, `refreshFx.ts`. Primitive: *reshape* `commitImport`. **Rejected** — it complects a currently-pure storage primitive with a history concern, and the only upside (shared transaction) isn't real, since the snapshot targets a different object store. The flag exists solely to remember the FX-path exclusion that Approach 1 gets structurally.

## 4 Shapes (from develop-perspective)
- **Nature**: a tree's growth rings — write-once, date-keyed records; the chart *connects the rings* and stays honest about sparseness (ordinal X axis, no synthetic daily fill).
- **Domain**: the **portfolio snapshot** is the load-bearing noun — a recon/ledger checkpoint. Natural slice: import (event) → snapshot (ledger entry) → charts (reporting). Snapshot must be stamped with its `baseCurrency`; staleness (`isStale`) is inherited from the existing model.
- **Theory**: the store is an immutable **event log**; `lib/analytics.ts` functions are pure **left folds** over it. Date-keyed `put()` is an **idempotent upsert** ("today's snapshot"). End-to-end argument: chart correctness lives in aggregation, Recharts stays a dumb projection.
- **Implementation**: smallest spike — add `recordSnapshot()` after `commitImport` at `PreviewStep.tsx:50`, copy the staged `upgrade` shape from `storage/holdings.ts:42`. Hidden friction: the `refreshFx` second caller forces the write into `PreviewStep`; Recharts' default theme fights the `ink/bone/tick` tokens — budget real SVG-level restyle time.
- **Tensions**: (1) Nature ("sparse is honest") vs. Recharts default continuous time axis → use an ordinal/categorical X axis, one tick per snapshot day. (2) P&L-over-time is theoretically a redundant fold over the same log as value-over-time → design them as one visual pair (shared X axis, P&L as the gap between value and invested), not two independent widgets.

## Picked Reliability Tenets (from reliability-tenets)
- **Tenet 2 (simple critical path)**: the v3 migration runs in `getDB()` before any route renders — keep the `oldVersion < 3` branch to a single `createObjectStore`, no backfill inside `upgrade`. Lazy-load (`React.lazy` + `Suspense`) the ~100KB+ Recharts bundle so first paint isn't gated on it.
- **Tenet 3 (blast radius)**: `recordSnapshot()` in try/catch (`console.warn` only, never blocks import); each chart behind an error boundary so one bad chart degrades to a placeholder; `valueSeries()` tolerates old-shape / different-base records instead of throwing.
- **Tenet 6 (rollout + rollback)**: gate the feature behind `FEATURE_HISTORY` in `featureFlags.ts` (mirrors `FEATURE_BASE_CURRENCY`). The v3 migration is **not** rollback-able (a v2 build can't reopen a v3 DB) — so it must be purely additive, and rollback = `FEATURE_HISTORY=false` + redeploy, leaving the schema at v3. Playwright must prove both fresh-DB (v0→v3) and upgrade (v2→v3) paths before the PR goes ready.
- **Tension**: Tenet 2 (minimal migration) vs. the feature — resolved by the `upgrade` callback doing exactly one `createObjectStore`; all snapshot population happens lazily on the next import.

## Pre-mortem
- **Most likely failure**: the v3 migration throws or races, `getDB()` → `dashboardLoader` rejects, and the whole app errors out (not just a chart) for users with existing v2 data; reloading doesn't fix it because IndexedDB has partially bumped. Second: `valueSeries()` hits a zero `avgBuyPrice` or single-snapshot history → `NaN` axis ticks → Recharts render throw white-screens `/analytics`.
- **Rollback**: two-layer. UI — flip `FEATURE_HISTORY=false` + redeploy. Per the implementation decision (2026-05-16): the flag gates *only the schema-dependent surface* — the snapshot write and the two time-series charts (`ValueOverTime`, `PnlOverTime`). The reworked KPI row, allocation donut and top-movers chart are pure folds over current holdings, cannot be broken by the history store, and stay rendered with the flag off — so no legacy `AnalyticsRoute` code is retained. Schema — never revert `DB_VERSION`; the additive v3 store sits unused with the flag off. Both the v0→v3 and v2→v3 paths are Playwright-tested pre-merge.
- **Detection + responder**: single-user static app, no telemetry — detection is the draft-PR Playwright gate (load `/analytics` with seeded holdings and with a seeded v2 DB; `browser_console_messages` clean; four charts captured in default + `<2`-snapshot empty states). Responder is the PR author reviewing the `## Evidence` comment before ready-for-review. There is no post-merge second line of defence, so the migration + empty-state paths must be proven in Playwright before merge.

## Recommendation
Take **Approach 1**: write the history snapshot from `PreviewStep` after `commitImport` resolves, in a new `storage/history.ts`, behind a `FEATURE_HISTORY` flag. It keeps `commitImport` pure and structurally excludes the FX-refresh caller — Approach 2's flag exists only to re-derive that exclusion by hand. Main tradeoff the user can redirect: the snapshot write is best-effort (not atomic with the commit), so a rare post-commit failure leaves a one-day history gap — acceptable since holdings remain the source of truth and the gap is cosmetic. Build order: (1) schema migration + `history.ts` + flag, (2) `PreviewStep` snapshot write, (3) `lib/analytics.ts` pure folds + unit tests, (4) Recharts charts + KPI rework + lazy-load/error boundaries, (5) Playwright verification of both DB-migration paths and chart empty states. Tests needed: unit tests for `analytics.ts` (allocation, topMovers, valueSeries — including zero-price and single-snapshot edge cases) and for `history.ts` (date-keyed upsert / same-day overwrite).
