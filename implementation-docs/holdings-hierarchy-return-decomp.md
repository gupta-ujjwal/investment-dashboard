> Generated by `/brainstorm` on 2026-09-07. Working notes at `notes/holdings-hierarchy-return-decomp/`.

## Frame

- **Kind**: feature (return decomposition — new pure-fold analytics + UI) bundled with an independent UI/CSS fix (holdings-table hierarchy) — user's explicit pairing choice, not because the two share implementation surface. Ship as two separate branches/PRs (see Recommendation).
- **Files/modules likely touched**:
  - Item 02: `src/components/HoldingRow.tsx`.
  - Item 06: new `src/lib/returnDecomposition.ts` (+ test), a new UI card on `PortfolioRoute.tsx` wrapped in `ChartErrorBoundary`.
- **Slice(s) / component(s)** (`productContext/architecture.md` vocabulary): Storage Layer (`arch-storage`, read-only), Analytics Engine (`arch-analytics`), Component/Module Map (`arch-component-map`).
- **External surface affected**: none. No new IndexedDB store, no `DB_VERSION` bump, no new network egress, no change to `refreshFx.ts`'s stamping logic. Item 06 is a pure read-side fold over already-embedded `historySnapshots` data.
- **Out of scope** (explicit):
  - True lifetime-since-actual-purchase FX decomposition — the data model has no memory of the FX rate at purchase (`refreshFx.ts` overwrites `avgBuyPriceBase` with `avgBuyPrice × rate_now` on every refresh, confirmed the only assignment site in the codebase). Only "since a recorded snapshot" is buildable without a data-model change.
  - An explicit lot/open-close-boundary data model (would defeat 3 of the 4 edge cases below at the root) — a genuinely larger re-architecture (touches `CanonicalHolding`, every consumer, likely a schema bump), sized for its own future brainstorm, not this feature. Named explicitly here as a deliberate scope boundary, not an oversight (raised and triaged in Step 5 review).
  - Row-level import preview (03), duplicate-row picker (07) — separate roadmap items.
  - Return decomposition for manual assets (`ManualAsset` has no `quantity`/unit-price split — the 3-leg formula doesn't apply to a value-only entry). Holdings-only in this plan.

## Research summary

**Item 02** — `src/components/HoldingRow.tsx:180-243`: every numeric cell is `font-mono text-sm` (14px/400); only the instrument name (`:188`) is `font-semibold`. `profitColor` (`:53-57`) is already the single exported source of truth for gain/loss color, reused by `HoldingsTable.tsx`'s footer (`:108-118`), which already applies `font-semibold` to its Value total — the one place in the current table doing what item 02 asks, extending it upward into the body rather than inventing a new hierarchy language. `OverviewRoute.tsx`'s `Kpi` component (size + color + a rail swatch, not color alone) is the house style to match.

**Item 06** — `src/lib/refreshFx.ts:14-32` stamps `avgBuyPriceBase`/`currentPriceBase` from the *same* `rate` argument on every call, and `refreshFx()`/`applyManualRate()` (`:117-155`) re-stamp every holding on every refresh — confirmed via `grep -rn "avgBuyPriceBase:\|currentPriceBase:" src/` returning exactly one assignment site. There is no purchase-time-rate memory anywhere. `HistoryRecord` (`src/storage/history.ts`) embeds full `CanonicalHolding[]` copies per calendar day, each carrying its own `fxRate` as of that day — confirmed live against a worked 5-import scenario (published as an artifact this session) that a later FX refresh moves a holding's `avgBuyPriceBase` even when its native-currency cost basis never changed. `recordSnapshot` dedupes one-per-calendar-day (`history.ts`), so multi-year history caps in the low thousands of records — cheap to scan once per render.

Four edge cases surfaced and confirmed real (grill loop + Step 5 review), each with a code citation:
1. **Frozen/stale embedded rate** — a holding's embedded values only change in a snapshot captured after *that holding's source* is re-imported; two snapshots both falling between imports embed byte-identical values, decomposing to mechanically-correct-but-misleading all-zero legs. `DerivedRow.isStale` (`src/lib/holdingsView.ts:53`) is the existing precedent signal to reuse.
2. **Closed → reopened** — `src/storage/holdingMerge.ts:23-25`'s own doc comment: the closed→open flip on re-import happens in the *caller* (`PreviewStep.tsx`), which also lets the broker overwrite `avgBuyPrice`/`quantity` on that flip. A window spanning a close-then-rebuy would silently merge two economically unrelated holding periods.
3. **Cross-base-currency** — `src/lib/sinceLastVisit.ts:72-82` (`changeSinceLastImport`, shipped in PR #61) is the precedent: refuses (`undefined`) rather than guesses when two snapshots' `baseCurrency` differ.
4. **Assets vs. holdings** — `stampAsset` (`refreshFx.ts:52-73`) FX-stamps assets, but `ManualAsset` has no `quantity`/unit-price split; the 3-leg formula doesn't apply.

**Decomposition math** (pinned during Step 5 review, to close a real gap the review found — the leg order matters, naive decomposition doesn't sum exactly without picking one): for a window `(q₀,p₀,fx₀) → (q₁,p₁,fx₁)`,
```
qty leg   = (q₁ − q₀) · p₀ · fx₀     // shares added/removed, valued at the window-start price & FX
price leg = q₁ · (p₁ − p₀) · fx₀     // price move on the ending quantity, at window-start FX
FX leg    = q₁ · p₁ · (fx₁ − fx₀)    // FX move on the ending position
```
This order sums **exactly** to `ΔV = q₁·p₁·fx₁ − q₀·p₀·fx₀` with no residual (verified algebraically and against real numbers from the worked scenario: NVDA and AAPL both reconciled to the cent). Pinning this order is what turns "the legs should roughly explain the total" into "the legs sum to the total by construction" — the reconciliation check below becomes a true invariant, not a fuzzy sanity check.

## Approaches considered

### Item 02: Extend the existing Kpi/footer hierarchy language into the row (single approach)

- **Scope**: `HoldingRow.tsx`'s Value and Profit cells (desktop `<tr>` and mobile `<article>`) gain size/weight distinction, reusing `profitColor` — no new color logic.
- **Files**: `src/components/HoldingRow.tsx` only.
- **Key risks**: wider cells could push the 9-column desktop table into horizontal scroll at 1024-1280px — caught by a Playwright check at that width, not theoretical.
- **Complexity**: small. ~4 desktop cells + mobile-card equivalents, zero logic change.

### Item 06: Since-last-snapshot decomposition (recommended)

- **Scope**: `decomposeSinceLastSnapshot(history, baseCurrency) -> HoldingDecomposition[]`, diffing only the two most recent snapshots per holding — sibling module to `sinceLastVisit.ts`, same refusal discipline, producing 3 reconciling legs per holding instead of 1 combined delta.
- **Files**: new `src/lib/returnDecomposition.ts` (+ test), a card on `PortfolioRoute.tsx` wrapped in `ChartErrorBoundary` — its **only** consumer, so rollback is a single-file revert with zero ripple into any other analytics surface.
- **Edge-case resolution, each now concrete** (revised after Step 5 review):
  1. **Frozen rate** — bounded window keeps the staleness exposure small; the card surfaces a per-holding "no fresh data since `<date>`" caveat (reusing `DerivedRow.isStale`'s signal) whenever a holding's `importedAt` predates the window-start snapshot — framed as a sampling limit, never as "no change" (a same-day double-import can still alias to zero, so the copy must be honest about *why* a zero is showing, not just that it is).
  2. **Closed → reopened** — narrative argument (two-snapshot windows are too narrow for a full close-then-rebuy cycle to land inside one, since `recordSnapshot` dedupes to one-per-day) is now backed by an **enforced runtime guard**, not just reasoning: if the window-start snapshot has a holding `closed` and the window-end has the same `[source, sourceSymbol]` `open`, the fold explicitly returns `undefined` for that holding rather than computing a number. A dedicated test fixture constructs exactly this transition and asserts the refusal — written first, before the happy-path tests.
  3. **Cross-base-currency** — identical guard to `changeSinceLastImport` (`sinceLastVisit.ts:72-82`), copied verbatim: refuse if the two snapshots' `baseCurrency` differ from each other or from current `settings.baseCurrency`.
  4. **Assets** — out of scope for v1 (Frame).
- **Reconciliation invariant** (new, from Step 5 review): every computed `HoldingDecomposition` asserts `qtyLeg + priceLeg + fxLeg ≈ ΔV` within a `0.01` base-currency epsilon before being returned — this is not defensive theater, it's the direct consequence of pinning an exact-summing leg order, checked at runtime so a future refactor that breaks the invariant fails loudly (a thrown error inside `ChartErrorBoundary`, which *is* the right containment tool for an assertion failure, as opposed to a silently-wrong number, which it is not).
- **Key risks**: only answers "how did the last period go" — permanently forfeits "how has this position done since I bought it," which was the original product motivation. This is a real, deliberate capability tradeoff, not merely "less risky" — owned explicitly in the Recommendation below, not hidden inside a risk bullet.
- **Complexity**: small-medium. Pure fold, one new file, reuses every existing R1/error-boundary/staleness pattern in the codebase.

### Item 06: Since-first-snapshot ("lifetime") decomposition — deferred, not built in this plan

- **Scope**: per holding, find the correct window-start by walking `getHistory()` back to the start of the holding's current open "streak" (the first snapshot after its most recent closed→open transition, or true first appearance if none), then diff against latest.
- **Why deferred**: the window-resolution walk is the single highest-risk piece of logic in the entire feature space — untested-until-written, and a bug in it produces a *plausible, non-crashing, wrong* number rather than a visible failure (exactly the failure mode the user's "no mistakes" bar is most worried about). Both Step 5 reviews independently converged on deferring this. Two concrete preconditions before it's ever built: (a) the closed→open transition-detection rule must be pinned against the real schema (explicit `status` field transition vs. inferred from row presence — not decided here, deliberately, since designing it now for code not being written is speculative), and (b) the window-resolution helper must ship with its own adversarial test suite — the close→reopen fixture written before any happy-path test — as an independently unit-tested pure function, not folded into the same commit as the rest of the feature.
- **Complexity**: medium-large, dominated entirely by the correctness of (a).

## 4 Shapes (from the develop-perspective review sub-agent)

- **Nature**: item 02 is unremarkable Gestalt visual-weight. Item 06's frozen-rate edge case is a textbook aliasing artifact (sampling a moving process too infrequently makes it look stationary); the closed→reopened edge case is a braided-river pattern — a channel that dries and re-forms elsewhere is a new channel, not a continuation.
- **Domain**: the load-bearing nouns (holding, snapshot, FX rate, base currency) are NAV/accounting vocabulary, and snapshot-diffing is the domain-correct anchor. But 3 of the 4 edge cases trace to one root cause — `avgBuyPrice`/`avgBuyPriceBase` are overwritten scalars, not an appended lot ledger — which both approaches work around rather than fix. Named explicitly as an out-of-scope, deliberate boundary (see Frame), not an oversight.
- **Theory**: the qty/price/FX decomposition is order-dependent — a real gap neither original approach doc addressed. Resolved by pinning the exact summing order (Research summary above), turning "legs approximately explain the total" into "legs sum to the total exactly, checked at runtime."
- **Implementation**: item 02's one real risk (1024px horizontal scroll) is already concretely gated by a Playwright check. Item 06 Approach 2's cost/mechanism claims were under-specified for a deferred approach — correctly left unspecified rather than speculatively designed for code not being written.
- **Tensions**: Approach 1 for item 06 isn't merely "the same feature with risk removed" — it permanently forfeits lifetime-since-purchase, which was the original ask's motivation. Owned explicitly in the Recommendation, not framed as free.

## Picked Reliability Tenets (from the reliability-tenets review sub-agent)

- **Tenet 2 (critical-path simplicity)**: the decomposition fold *is* the critical path, since the bar is "no reporting mistakes." Approach 2's window-resolution walk is new, untested-until-written logic on that exact path — deferred rather than attempted in v1.
- **Tenet 4 (early/automatic detection, translated for a telemetry-free single-user app)**: the reconciliation invariant (legs sum to the observed total) is the single highest-leverage correctness gate available, and now ships as a runtime-checked property, not an implicit assumption.
- **Tenet 3 (blast radius)**: `ChartErrorBoundary` only contains thrown exceptions — it does not protect against a silently-wrong, non-throwing number. The reconciliation assertion is the actual containment mechanism for this feature's specific risk; the error boundary remains for its own, separate purpose (a genuine crash).
- **Tenet 7 (adversarial verification)**: Approach 1's "can't happen in a 2-snapshot window" argument, originally narrative-only, is now an enforced runtime guard plus a dedicated adversarial test fixture (written first) — not left resting on the reasoning staying true forever.
- **Tenet 6 (rollback readiness)**: `returnDecomposition.ts` has exactly one consumer, wrapped in `ChartErrorBoundary` — rollback is a single-file `git revert` with zero ripple, stated explicitly rather than left implicit.

## Pre-mortem

- **Most likely failure**: a holding whose source hasn't been re-imported recently shows all-zero legs next to holdings showing real movement, read as "hasn't moved" rather than "no fresh data" — asymmetric import cadence across two brokers is the *normal* case for this app, not an edge case, so the per-holding staleness caveat ships in the same commit as the fold, not as a follow-up.
- **Rollback**: item 02 — `git revert` on one commit, no flag needed. Item 06 — `git revert` on the card's introducing commit(s); zero ripple (single consumer); no `DB_VERSION` change either direction. Ships without a feature flag *conditional on* the reconciliation runtime guard being in place — if that guard is dropped for any reason during implementation, add a `FEATURE_RETURN_DECOMP` canary gate (same precedent as every other analytics surface) rather than shipping unguarded.
- **Detection + responder**: no telemetry (hard constraint). The reconciliation assertion plus two adversarial test fixtures (close→reopen-within-window, cross-base-currency) written *before* the happy-path tests are the only pre-merge gate available — a test suite that skips those two specific fixtures would pass while a wrong number ships. Responder is the maintainer, no on-call, same posture as every other feature in this repo.

## Recommendation

Ship as **two separate branches/PRs** — nothing in the two items shares implementation surface, and item 06 carries a financial-correctness bar item 02 doesn't, so gating one on the other's review buys nothing.

**Item 02** ships as-is — small, low-risk, single approach, Playwright-gated at the one real risk width. Ready for `/develop` immediately.

**Item 06 — superseded 2026-09-07.** After seeing a worked example of what "since last snapshot" actually shows (stale-flagged zeros for infrequently-imported holdings, brand-new positions excluded, no answer to "how has this position done since I bought it"), the user explicitly rejected Approach 1 as not worth building: *"there is no point of building this half baked feature... lets build it properly... attribute for each holding the value/percentage due to fx rate change and actual price increase... over the whole history of user's entry in the stock."*

**Approach 2 (lifetime since entry) is now the chosen direction — not deferred, but also not ready to build yet.** Its precondition from the Step 5 review still holds and is now load-bearing rather than optional: the closed→reopened window-resolution mechanism (finding the correct "first snapshot" for a holding that may have been fully sold and later rebought) must be designed — concretely, against the real `historySnapshots` schema, with an explicit detection rule (not "inferred somehow") — and given its own adversarial test suite (the close→reopen fixture written before any happy-path test), **before** `returnDecomposition.ts` is written. That design work did not happen in this brainstorm pass (it was explicitly out of scope pending this exact decision) and is the next step, not implementation.

Everything else this plan already resolved carries forward unchanged into Approach 2: the pinned qty→price→FX leg order (sums exactly, no residual), the reconciliation runtime assertion, the cross-base-currency guard (reused from `sinceLastVisit.ts`), the stale-data caveat per holding, and the holdings-only v1 scope (assets excluded).
