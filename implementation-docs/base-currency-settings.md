# Plan: base-currency-settings

> Generated by `/brainstorm-lite` on 2026-05-15. Working notes at `notes/base-currency-settings/`.

## Frame
- **Kind**: feature
- **One-line summary**: Add a user-configurable base currency (default INR) stored in a new IDB settings store. Stamp `fxRate`/`fxAsOf`/`avgBuyPriceBase` on every holding at import-commit and on an explicit Settings "Refresh FX" click. Frankfurter as the FX source (CORS-open, no key, ECB daily). Holdings/Analytics stay read-only over stamped values.
- **Files/modules likely touched**:
  - `src/storage/holdings.ts` — add optional `fxRate`/`fxAsOf`/`avgBuyPriceBase` to `CanonicalHolding`; bump `DB_VERSION` 1 → 2 to register a new `settings` object store.
  - `src/storage/settings.ts` (NEW) — singleton-row helpers `getSettings()` / `saveSettings()` / `updateFxMeta()`.
  - `src/lib/fx.ts` (NEW) — `fetchUsdInrRate(): Promise<{ rate, fetchedAt }>` over `https://api.frankfurter.dev/v1/latest?from=USD&to=INR`, with 3s timeout and response validation (rate must be finite, 1 < r < 1000).
  - `src/routes/SettingsRoute.tsx` — rewrite: profile form (name + base radio + locale radio) on top, FX meta panel (last rate / last refresh ts / "Refresh FX" / "Save & refresh FX" button / manual-rate paste fallback) below, import wizard moves below that.
  - `src/routes/import/PreviewStep.tsx` — `handleCommit` calls `fetchUsdInrRate()` before `commitImport()`; stamps each row of inserts/updates with FX fields; fail-soft to cached `lastFxRate`; if both fail, commits with `undefined` base fields.
  - `src/components/HoldingsTable.tsx` — desktop: new rightmost `Cost (≈ ₹/$)` column; mobile: `≈ ₹X,XXX` line under cost. `—` when `avgBuyPriceBase` is `undefined`.
  - `src/routes/AnalyticsRoute.tsx` — promote a `Total · ₹` (or `$`) KPI to slot 1, computed from the existing `aggregate()` reduce. If any holding has `undefined` base, render `—` + a "Refresh needed" chip.
  - `src/routes/HoldingsRoute.tsx` — loader fetches settings + holdings; show a "Refresh needed" banner above the table if any row has `undefined` base.
  - `src/App.tsx` — `FEATURE_BASE_CURRENCY` feature-flag const (soft-rollback rail); loaders updated to return `{ holdings, settings }`.
- **External surface affected**: One outbound HTTP call to `api.frankfurter.dev` per import-commit and per user-clicked Refresh. No body, no key, no PII. Triggered only by user action — no boot fetch, no scheduler.
- **Out of scope**: live unit prices, additional currencies beyond INR/USD, theme/avatar/email settings fields, auto-fetch on boot, FX-history snapshots, migration code for the v1 → v2 schema bump (user wipes and re-imports).

## Research summary
- IDB upgrade callback uses `oldVersion < N` guards — additive bump to v2 just appends another guarded branch (`src/storage/holdings.ts:33-43`). New `settings` store lives in the same DB; existing singleton `getDB()` serves both.
- `CanonicalHolding` is a flat record (`src/storage/holdings.ts:8-17`). New optional fields require no migration — old rows just have them absent, and IDB doesn't enforce shape.
- `commitImport` is a single read-write transaction (`src/storage/holdings.ts:63-73`). Refresh-all reuses this exact shape: `commitImport({ inserts: [], updates: stamped, deletes: [] })`.
- `handleCommit` (`src/routes/import/PreviewStep.tsx:22-39`) is the only writer in the import wizard. Already async with `commit-failed` action → adding `await fetchUsdInrRate()` before `commitImport` reuses the existing failure surface; no new wizard state.
- `diffHoldings` is structural, doesn't touch FX fields (`src/parsers/diff.ts:30-44`) — stamping FX post-diff leaves diff logic untouched.
- `aggregate()` already walks all holdings once branching on currency (`src/routes/AnalyticsRoute.tsx:153-173`). Adding `baseCost += qty * avgBuyPriceBase` (when defined) is a single line in the existing loop.
- `formatMoney(amount, currency)` is currency-aware via two pre-built `Intl.NumberFormat` (`src/lib/format.ts:1-17`). Reusable directly for the base-currency column header and values.
- Frankfurter probed live `2026-05-15T06:30Z`: `GET https://api.frankfurter.dev/v1/latest?from=USD&to=INR` → 200, `{"amount":1.0,"base":"USD","date":"2026-05-14","rates":{"INR":95.77}}`, `access-control-allow-origin: *`, `cache-control: public, max-age=86400`. Daily granularity (response `date` is yesterday's ECB rate). No API key.
- Currency conversion math: always fetch with `from=USD&to=INR` (one canonical rate). For base = INR + USD holding: `base = native * rate`. For base = USD + INR holding: `base = native / rate`. Invert in code, not in two API calls.

## Approaches considered

### Approach 1: Stamp at commit, fail soft *(recommended)*
- FX fetched inside `handleCommit` (preview-step) right before `commitImport`. Fail-soft to cached `lastFxRate`; if absent, commit with `undefined` base fields and surface "Refresh needed" banner.
- Refresh button shares one helper: fetch → getAll → map-stamp → commitImport-as-updates → updateFxMeta.
- Base-currency change uses the same path; button label flips to "Save & refresh FX" when there's a pending base change (Q7 = c).
- Net code: ~150 LOC + Settings UI rewrite. No new wizard states. No new failure modes (reuses `commit-failed`).

### Approach 2: Stamp at parse
- FX fetched inside `UploadStep` so `ParseResult.rows` already carry FX before `diffHoldings`. Preview gets richer numbers.
- Costs: every upload attempt hits Frankfurter even if the user abandons preview; second failure surface to design (parse-with-FX-pending state); no user-visible benefit because preview's base-currency display wasn't part of the brief.
- Rejected because the wins (base-currency preview) weren't requested and the costs are real.

### Approach 3: Read-side derive *(ruled out)*
- Store a single global `currentFxRate`; Analytics/Holdings derive `qty * avgBuyPrice * rate` in render.
- Violates the user's stated "no compute in read pages" rule. Also loses per-holding rate audit. Not viable.

## 4 Shapes (from develop-perspective)
- **Nature**: Stamping at commit has the shape of a photograph / tree-ring (sample a continuous field, freeze it). But the destructive **refresh button is anti-photographic** — it overwrites every previous freeze with today's rate. We accept that loss of history.
- **Domain**: Base currency is a *reporting/consolidation* concern, native-currency broker numbers are the truths. We deliberately drag the view computation into the import slice (materialized denormalization) because the user has forbidden read-time compute. The new field is an **approximation** of cost basis, not a true historical cost basis — UI should signal this with a leading `≈`.
- **Theory**: Materialized-view denormalization with explicit, manual cache invalidation (the Refresh button). Effects-at-the-edges (`fetchUsdInrRate` is the only IO) with a pure `stamp(holdings, rate)` transform fed through the existing transactional writer.
- **Implementation**: Codebase is unusually well-shaped — refresh-all is `commitImport({ updates: stamped })` over `getAll()`, ~15 lines. `aggregate()` extends by one branch. `handleCommit` adds one `await`. Smallest spike is feasible.
- **Tensions**:
  - *Nature ↔ user request*: lose FX history; "INR cost basis over time" chart isn't possible later without re-import. Acceptable for a personal dashboard where re-import is cheap.
  - *Domain ↔ user constraint*: materializing the view inside the row mislabels it as "cost basis"; mitigate with a leading `≈` in the UI ("≈ ₹X").
  - *Theory ↔ implementation*: snapshot store is theoretically right but 5-10× the code; destructive overwrite is right for now. Migration path (add `fx_snapshots`) stays open.

## Picked Reliability Tenets (from reliability-tenets)
- **Tenet 1 — Redundancy / graceful degrade**: Frankfurter is a single vendor. Plan has two-deep fallback (fetch → cached `lastFxRate` → `undefined` + banner). Add a **third tier**: manual rate paste input on Settings (~10 LOC) for fresh-wipe + offline situations.
- **Tenet 2 — Critical path simple**: import-commit is load-bearing; FX call now sits in it. Add a **3-second timeout** via `Promise.race` so a hung Frankfurter can't stall the commit click — on timeout, fall through to cache.
- **Tenet 3 — Blast radius**: refresh-all writes FX to every holding in one transaction. A `{"rates":{"INR":0}}` or missing-key response would NaN-poison the whole portfolio. Add **range validation** in `fetchUsdInrRate`: rate must be finite, positive, in `(1, 1000)`; throw otherwise. Single chokepoint, single guard.
- **Tenet 6 — Rollback**: IDB doesn't downgrade — once v2 writes, opening with v1 code is `VersionError`. Add **soft-rollback feature flag** `FEATURE_BASE_CURRENCY` at top of `App.tsx`; flipping it hides Settings/base-column without code surgery. **Hard rollback**: tag current `main` HEAD as `pre-base-currency` before merge so the user can `git checkout` + redeploy.
- **Tension**: Tenet 2 says don't add hops to critical path; Tenet 1 says it's OK if degrade is handled. Resolved — FX is "best effort" within commit (timeout + cache fallback), not a hard dependency.

## Pre-mortem
- **Most likely failure**: Refresh click fires while Frankfurter returns 200 with `{"rates": {}}` (or null INR, or content-type drift). `rate = undefined`, every holding gets `avgBuyPriceBase = NaN`, the transaction commits, all base-currency cells render `NaN` / `—`. Killed by Tenet 3's response validator.
- **Rollback**: Soft (preferred) — flip `FEATURE_BASE_CURRENCY = false` in `src/App.tsx`, redeploy. New UI hides; v2 schema stays intact (additive, no harm). Hard — `git checkout pre-base-currency && npm run deploy`, then clear site data to drop IDB v2.
- **Detection + responder**: No automated detection (privacy-first, no telemetry). Pre-merge: unit tests for `fx.ts` validator + stamp transform; Playwright run per `frontend-design.md` rule (verifies Holdings/Analytics render plausible base values, no `NaN` strings, no console errors). Post-merge: the user themselves; responder is the user; recovery action is the feature flag.

## Recommendation
**Take Approach 1 with the four reliability rails layered on**: 3-second `Promise.race` timeout, response range-validation in `fx.ts`, manual rate paste input as third-tier fallback, and `FEATURE_BASE_CURRENCY` feature flag plus `pre-base-currency` git tag for rollback. The main tradeoff the user can redirect: refresh is destructive and overwrites previous FX stamps — if/when historical FX queries matter, that needs a follow-up to add an append-only `fx_snapshots` store. For now, the simpler shape is right.
