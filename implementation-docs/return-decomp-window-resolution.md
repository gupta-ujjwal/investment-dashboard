## Research summary

**The fact that made window resolution simple**: `src/storage/history.ts:68-73` (`recordSnapshot`) calls `getAll()` on the *entire* `holdings` store, unfiltered, on every net-worth-moving event — every `HistoryRecord.holdings` is a full copy of every holding as of that moment (`history.ts:24-25`), not just the ones touched that day. Re-verified directly this session. Consequence: once a key `[source, sourceSymbol]` first appears in any snapshot, it appears in *every* subsequent snapshot, frozen if untouched — no gap/reappear pattern exists to detect. This is why "find the earliest snapshot containing this key" is a single well-defined linear scan, with no streak-detection algorithm needed — the hard problem this brainstorm was originally scoped to solve dissolved once the user also confirmed no closed→reopened special-casing is wanted at all.

**Everything else, carried from the prior brainstorm** (full detail in `implementation-docs/holdings-hierarchy-return-decomp.md`):
- No purchase-time FX rate is ever preserved (`refreshFx.ts:14-32,117-155` re-stamp every holding with the current rate on every refresh) — why the window must be snapshot-anchored.
- Decomposition formula (verified against real numbers in a published artifact this session): `qtyLeg = (q₁-q₀)·p₀·fx₀`, `priceLeg = q₁·(p₁-p₀)·fx₀`, `fxLeg = q₁·p₁·(fx₁-fx₀)` — sums exactly to `ΔV`, no residual.
- Cross-base-currency guard: `src/lib/sinceLastVisit.ts:72-82` is the exact precedent to copy — refuse rather than guess.
- Identity: `[source, sourceSymbol]` (`src/storage/holdings.ts:130-132`). `getHistory()` (`history.ts:76-80`) returns oldest-first, at most one record per calendar day.
- UI precedent: `AllocationBars` (swatch + label + pct + amount), `ChartCard`/`ChartErrorBoundary` bulkhead.

**New for this narrower brainstorm — the re-entry caveat and its consequence**: a `reenteredAfterClose` check (a genuine closed→open transition strictly inside the window — not merely "closed at some point," which a clean unreopened exit also satisfies) is a byproduct of the same linear scan, no second pass. `DerivedRow.isStale` (`src/lib/holdingsView.ts:53`) is the shape precedent (a boolean derived alongside the main computation, surfaced as a small UI marker).

**Path-dependence finding from Step 5 review** (the reason this plan's UI behavior differs from the original "just add a caveat label" framing): `totalDelta` is a true state function — it only depends on the window's start and end values, so it's honest regardless of what happened in between. The three legs are **not** — they're path-dependent (the performance-attribution analogue of heat/work in thermodynamics). When a window spans a closed gap, `priceLeg`/`fxLeg` (built from the endpoint prices/rates and the *ending* quantity) attribute price/FX movement to the entire span **including the period the holder owned zero shares** — not merely "two ownership periods merged into one number," but individually misleading legs. The reconciliation assertion (legs sum to total) is an algebraic identity that holds regardless, so it gives false confidence exactly in this case — it validates arithmetic, not meaning.

## Approach

Single approach — extends `sinceLastVisit.ts`'s exact shape (pure function, Map-based single pass, R1 refusal discipline) rather than inventing a new pattern. No competing architecture once the window-selection question resolved simply.

```ts
export type HoldingDecomposition = {
  source: BrokerSource
  sourceSymbol: string
  name: string
  windowStartDate: string
  windowEndDate: string
  totalDelta: number
  /** undefined when reenteredAfterClose is true — see the path-dependence
   *  note above. The UI shows totalDelta alone (a valid state function)
   *  plus a "can't be split across a closed period" line in that case,
   *  never the 3 legs — they'd individually misattribute movement to a
   *  period of zero ownership, not just merge two periods into one number.
   *
   *  A position closed once and never reopened does NOT hit this case:
   *  its price simply freezes from the close point onward (closed rows
   *  keep appearing, frozen, in every later snapshot — confirmed this
   *  session), so ownership was continuous right up to the close and the
   *  legs correctly show zero incremental movement during the frozen
   *  tail. Only a genuine re-entry (closed, THEN open again) creates a
   *  real zero-ownership gap in the middle of the window. */
  legs: { qtyLeg: number; priceLeg: number; fxLeg: number } | undefined
  /** True only for a genuine closed→open transition strictly inside the
   *  window (scanning forward: status went 'closed' at some snapshot, then
   *  'open' again at a later one) — NOT true for "closed at the very end
   *  and never reopened," which has no path-dependence problem. */
  reenteredAfterClose: boolean
}

export function decomposeHoldingReturns(
  history: readonly HistoryRecord[],
  baseCurrency: BaseCurrency,
): HoldingDecomposition[]
```

**Algorithm** (single pass over `getHistory()`'s oldest-first output, per-key bookkeeping in a `Map`):
1. For each record in order, for each holding, update `firstSeen`/`lastSeen` for that key. Also track `sawClosed` (seen `status:'closed'` at some earlier point in this forward scan) and `reenteredAfterClose` (set `true` the moment `sawClosed` is already `true` and we see `status !== 'closed'` again) — this distinguishes "closed once, stayed closed" (fine, legs stay valid) from "closed, then reopened" (the actual path-dependence problem), both single-pass, no extra scan.
2. Skip keys seen only once (nothing to diff). Skip keys whose first/last snapshot `baseCurrency` differs from each other or from the current `settings.baseCurrency` (refuse, R1 — same guard as `changeSinceLastImport`).
3. Compute `totalDelta` always. Compute the 3 `legs` **only when `!reenteredAfterClose`** — when `reenteredAfterClose`, `legs: undefined` by construction, per the path-dependence finding (Step 5 review + user confirmation).
4. **Reconciliation assertion**, scoped per-holding (Step 5 fix — was originally one throw for the whole batch): when legs are computed, assert `qtyLeg + priceLeg + fxLeg ≈ totalDelta` within a `0.01` epsilon. A mismatch marks **that one holding** as uncomputable (excluded from the returned array, or flagged — implementation detail for `/develop` to pick the cleaner shape) and logs via `console.warn`, matching this session's established best-effort pattern (`recordSnapshot`'s own try/catch in `PreviewStep.tsx`) — it does **not** throw out of the whole function, so one bad row never blanks the table for every other holding.
5. Return in first-encountered order (stable, deterministic); sorting is a UI concern, not baked into the pure fold.

**Files/modules**: new `src/lib/returnDecomposition.ts` (+ test), `src/featureFlags.ts` (+1 flag), a new card/section on `PortfolioRoute.tsx` wrapped in `ChartErrorBoundary` (which remains for genuine crashes — malformed input reaching the function at all — not for a single row's arithmetic disagreement, which is now handled inside the fold itself).

**Key risks**: a position that's been open the whole history gets a real, meaningful, fully-decomposed lifetime number. A position that was closed and reopened gets an honest total with legs explicitly withheld, not a fabricated-looking split. A reconciliation failure on one holding degrades that one row, never the whole panel.

**Complexity**: small. One linear pass, no window-resolution algorithm, one extra display-time branch (`reenteredAfterClose`) over the originally-scoped design. Test matrix: single-snapshot key (skip), 2+ snapshot key with legs (compute + reconcile), cross-currency window (refuse), closed-then-reopened key (`legs: undefined`, `reenteredAfterClose: true`, `totalDelta` still computed and correct), closed-and-never-reopened key (legs still computed, to the frozen exit values — `reenteredAfterClose` stays `false` here by design, since a clean unreopened exit has no zero-ownership gap), a reconciliation-failure fixture (marks one row, doesn't throw), and a real-`historySnapshots` dry run (not just synthetic fixtures) before the flag is flipped.

## Pre-mortem

- **Most likely failure**: an unusual real holding history (a split, a multi-year gap spanning several FX regimes) fails the reconciliation assertion — now degrades to one "couldn't compute" row, not a blanked panel. Second: a user sees "can't be split across a closed period" and is confused without more context — mitigated by specific copy naming the cause.
- **Rollback**: `git revert` → redeploy; `FEATURE_RETURN_DECOMPOSITION=false` is the cheap first line (no redeploy needed pre-flip). No `DB_VERSION` change. Single consumer, zero ripple.
- **Detection + responder**: no telemetry. Three-layered: the now-correctly-scoped per-holding assertion; a real-data dry run before the flag flips; the `reenteredAfterClose` UI branch itself as a product-level detection signal ("this number's shape is different here"). Responder is the maintainer, no on-call.

## Recommendation

Ready for `/develop` — no open design questions remain. `reenteredAfterClose` (not the coarser "was ever closed") is the precise condition for suppressing legs, resolved while writing this plan: a clean, unreopened exit has no zero-ownership gap (its price simply freezes at close, per this session's own confirmed snapshot behavior), so it keeps its legs; only a genuine closed→open re-entry inside the window loses them. Ships behind `FEATURE_RETURN_DECOMPOSITION=false`; flip after a Playwright evidence pass against both synthetic fixtures and a real-shaped multi-gap portfolio.
