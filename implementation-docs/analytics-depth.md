## Approaches considered

### Approach 1: Single PR, single feature flag

One PR introduces `FEATURE_ANALYTICS_DEPTH` (one compile-time flag). All four widgets + their data + the GH Actions refresh workflow behind that one flag. Rejected: rollback is binary; sector data review + analytics math review are mashed; review fatigue.

### Approach 2: Two PRs — pure-fold widgets first, data-pipeline widgets second (RECOMMENDED)

Splits along the natural data-dependency seam.

- **PR A**: Concentration KPI sub-row + Currency Exposure donut. Pure folds over `DerivedRow[]`. No new bundled data. Behind `FEATURE_ANALYTICS_DEPTH` (single flag, off by default, flipped on in same PR once playwright + unit fixtures green).
- **PR B**: Sector donut + Benchmark overlay. Adds `src/data/sectors.json`, `src/data/benchmarks/*.json`, `scripts/refresh-benchmarks.mjs`, `scripts/validateData.mjs`, `.github/workflows/refresh-benchmarks.yml`. Per-widget sub-flags `FEATURE_SECTOR_DONUT` and `FEATURE_BENCHMARK_OVERLAY`; both default off in PR-B commit, flipped on in separate one-line commits once each widget's evidence is green.
- PR B opens as draft against PR A's branch so review parallelises; auto-retargets to `main` when PR A merges.

### Approach 3: Single PR, four independent feature flags

One PR, four flags (`FEATURE_CONCENTRATION_KPI`, `FEATURE_CURRENCY_EXPOSURE_DONUT`, `FEATURE_SECTOR_DONUT`, `FEATURE_BENCHMARK_OVERLAY`). Rejected: observed failure modes cluster on the data-dependency axis (two regions: pure-fold widgets, external-data widgets). Four flags over-fit the failure space; two flag regions match the natural partition. Sprawl and dead-code-drift risks added on top.

## 4 Shapes (from the develop-perspective review sub-agent)

- **Nature**: Four widgets are not a uniform bundle. Two are downstream folds of in-memory holdings (fast-tide); two are downstream of external substrate that has its own watershed (slow-tide). Forcing them through one PR ignores that one side fluctuates on its own clock. Benchmark JSON is a slow-tide signal stitched into a fast-tide UI — stale-ness must be *visible*, not silent.
- **Domain**: Pure-fold widgets respect every existing rule (R1, R6, R9, R10). Sector taxonomy is domain-shaped: GICS for USD-listed, NSE classification for INR-listed — no unified ontology, both coexist honestly. Mixed-currency benchmark overlay is misleading by construction (apples-to-oranges) — hide it with a caveat, don't silently pick one index.
- **Theory**: Pure folds over `DerivedRow[]` are the right abstraction. Benchmark is the only widget that's a different shape — time-series alignment + normalization (rebase to portfolio-start, forward-fill non-trading days, clip to overlap). Concentration metrics are not unique — Top-5 weight, HHI, single-stock flag picked; ENB and Top-1 rejected with reasoning.
- **Implementation**: Strong grounding in the existing codebase. Under-specified areas (CI failure surface, date alignment, bundle budget, Playwright cost in two-PR mode) all surfaced and addressed in the recommendation.
- **Tensions**: Nature vs Process — two-watershed split wants two PRs; Playwright runs twice. Process cost named and accepted. Domain vs Theory — easy time-series overlay theory says "just rebase"; domain says "mixed-currency portfolio is meaningless to overlay"; resolved by hiding the line + legend caveat. Domain vs Implementation — one JSON file encodes the taxonomy choice; choice made deliberately (GICS + NSE, not unified).

## Picked Reliability Tenets (from the reliability-tenets review sub-agent)

- **Tenet 3 (Blast radius)**: Per-widget blast radius — a bad `sectors.json` entry mis-allocates one donut slice; a malformed `benchmarks/*.json` row can crash one chart. Per-widget flags + `ChartErrorBoundary` + fold-returns-`[]`-on-malformed are the bulkhead.
- **Tenet 4 (Early detection)**: No runtime telemetry. Build-time signals do the work: `scripts/refresh-benchmarks.mjs` validates fetched series before writing JSON; `scripts/validateData.mjs` runs in `prebuild` and fails red on malformed shape.
- **Tenet 6 (Staggered rollout + rollback)**: Approach 2's two-PR + per-widget-flag structure is the right read of this tenet. Feature flags here are pre-merge dark-shipping, not post-deploy kill switches — once deployed, rollback = `git revert && git push` → existing `deploy.yml` redeploys in ~2 min.
- **Tenet 7 (Test the limits)**: Named edge-case unit fixtures replace the impossible-on-static-site canary. Playwright + unit fixtures are the canary gate — flags do not flip on until both are green.

## Pre-mortem

- **Most likely failure**: Six weeks post-PR-B, a weekly `refresh-benchmarks.yml` PR with a malformed close value (e.g. NaN-coerced from a bad upstream cell on a holiday-bordered weekend) is rubber-stamped by a maintainer. Build doesn't catch it if validators are too permissive (e.g. `typeof === 'number'` vs `Number.isFinite()`). Users loading `/analytics` see the benchmark `ChartErrorBoundary` fallback ("Chart unavailable") on `ValueOverTime`. Other charts unaffected.
- **Rollback**:
  1. *Fast* (~2 min): `git revert <bad-commit> && git push` → existing `deploy.yml` redeploys with previous-good JSON. No IndexedDB migration needed (bundle-only data).
  2. *Scalpel* (~30s flip + ~2 min redeploy): set `FEATURE_BENCHMARK_OVERLAY = false`, push one-line commit, redeploy. Sector donut and rest of page stay live; only the benchmark line goes dark. Preferred for benchmark-only incidents.

  PR A widgets are unaffected by any PR B rollback — they have no bundled-data dependency.
- **Detection + responder**: No runtime telemetry by doctrine (R10 + no-first-party-telemetry per `CLAUDE.md`).
  1. **Build-time** (primary): `npm run validate:data` in `prebuild` fails red on malformed JSON; bad data never ships. Responder = PR author / merger.
  2. **Refresh-script-time**: `scripts/refresh-benchmarks.mjs` validates fetched series; failure → workflow red, no PR opened, previous-good JSON stays. Responder = maintainer reading repo Actions tab on next weekly run.
  3. **User-facing**: legend `as of YYYY-MM-DD` + >30d `stale` chip is the only visible signal. Responder = user / self-monitoring maintainer.

## Recommendation

Ship **Approach 2** — two PRs split along the data-dependency seam, with the 17 review findings folded into the design rules. PR A delivers concentration KPI + currency exposure (pure folds, ~small diff, ~one playwright round). PR B delivers sector donut + benchmark overlay + the build-time data validation + the weekly refresh workflow (per-widget flags, ~medium diff, second playwright round). Both PRs use `git revert` + redeploy as the post-deploy rollback; feature flags are the pre-merge dark-shipping mechanism and the deploy-time scalpel.

Main tradeoff: doubled playwright/evidence-capture cost for two PRs vs one. The user can redirect this by collapsing back to Approach 1 if the doubled cost outweighs the rollback-granularity + review-cognitive benefits.

What the user can redirect: PR split granularity (collapse to one PR), benchmark stale-banner threshold (defaulting to 30 days), HHI band thresholds (defaulting to DOJ standard), sector taxonomy choice (currently dual-ontology with no unification).
