# 4 Shapes — base-currency-settings (Approach 1)

## Nature
Stamping the rate at the moment of commit has the shape of a **photograph or tree-ring**: a continuous, flowing field (the FX rate stream) gets sampled and frozen into a discrete record. Same family as receipts, sediment layers, log structures — the natural shape for "record what was true at this moment". But the **refresh button is anti-photographic**: it re-stamps every row with today's rate, erasing the previous freeze. Tree rings don't get re-written when the climate changes; receipts don't update when prices do. The chosen shape is "all rows live in the same continuously-overwritten present", which fights the historical-record pattern that "stamp at commit" otherwise suggests.

## Domain
Base currency is a **reporting/consolidation concern**, not a transactional one — the broker's INR or USD numbers are the canonical truths, and base-currency is the rolled-up view *over* those truths. In domain-slice terms (import → reconcile → view), it logically belongs in the view slice. Approach 1 deliberately drags it into the import slice (materializing the view inside the row), because the user has forbidden compute in the view slice. The vocabulary here matters: `avgBuyPriceBase` is not really "the cost basis in INR" of a USD holding — true cost basis would need FX-at-purchase, which we don't have. We're storing an *approximation labelled cost basis*; worth being honest about that in code comments or the column header ("≈ ₹X" not "₹X").

## Theory
This is **materialized-view denormalization**, with `fxRate`/`avgBuyPriceBase` as the cached derived columns over the (`avgBuyPrice` × FX) source. The standard denormalization tax is cache invalidation, and the design pays it explicitly: refresh is the manual invalidator. The clean theoretical bit of Approach 1 is **effects-at-the-edges**: `fetchUsdInrRate` is the only effect; everything inside is a pure `stamp(holdings, rate)` transform fed through the existing `commitImport` transaction. The unclean bit is that refresh is **destructive**, not a snapshot — we have temporal data (`fxAsOf`) without temporal queries, so the timestamp is informational, not load-bearing. A snapshot-store design (append-only `fx_snapshots`, holdings carry a `fxSnapshotId`) is theoretically nicer but 5-10× the code and only pays off if you want history queries later.

## Implementation
The existing code is unusually well-shaped for this — `commitImport` (`src/storage/holdings.ts:63-73`) is already a single transaction over inserts/updates/deletes, and refresh-all is just `commitImport({inserts:[], updates: stamped, deletes:[]})` over `getAll()`. `handleCommit` (`src/routes/import/PreviewStep.tsx:22-39`) is already async with a `commit-failed` action, so adding one `await fetchUsdInrRate()` before it doesn't add a new failure surface — it reuses the existing one. `aggregate()` (`src/routes/AnalyticsRoute.tsx:153-173`) already walks holdings once and branches on currency; one more `if (h.avgBuyPriceBase !== undefined) baseCost += qty * baseAvg` line slots in. The smallest spike of the whole refresh feature is ~15 lines. **The only thing implementation flags that the diagram doesn't**: the FX call from `handleCommit` runs *before* `commitImport`, so a slow Frankfurter response (e.g., 2s) adds latency to the commit button. Mitigation: show the spinner immediately on click; the UI already has a "committing" state for this.

## Tensions
- **Nature ↔ user request.** Nature says "stamp historical, derive current". User says "overwrite all rows on refresh, derive nothing". User wins. Cost: no "INR cost basis over time" chart is possible later without a re-import — we only ever know one rate.
- **Domain ↔ user constraint.** Domain says base currency is a view concern; user says no compute in views. Resolved by materializing the view into the row (Approach 1). Cost: the column is misleadingly named `avgBuyPriceBase` (sounds like a cost basis) when it's actually "qty's worth of base currency at last-known FX rate". Honest column header in the UI ("≈ ₹X" with the ≈) is the cheap fix.
- **Theory ↔ implementation.** Snapshot store is theoretically right, destructive overwrite is implementationally right *for now*. Migration path is clean: if/when history becomes interesting, add `fx_snapshots` and have refresh `INSERT` instead of `UPDATE` the FX columns. The shape doesn't trap us.

## Recommendation
Approach 1 is right for the constraints the user has set. The tensions are real but the costs are bounded: losing FX history is acceptable for a personal dashboard where re-import is cheap, the misleading naming is a one-line UI fix, and the snapshot-store upgrade path stays open. The one thing worth pushing back on: in the UI, render the base-currency column with a leading `≈` glyph so the user (in six months, looking at their own dashboard) doesn't read it as "the cost basis I paid in INR" — because it isn't.
